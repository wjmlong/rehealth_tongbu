# 根据项目数据库生成测试数据提示词

你是一名资深 Java 后端工程师、数据库工程师和测试工程师。

现在请你基于当前项目的真实数据库结构，为项目生成一套**可直接用于开发环境、测试环境的高质量测试数据**。

你的目标不是简单随机 INSERT，而是生成：

- 符合真实数据库结构
- 符合字段约束
- 符合业务逻辑
- 符合表之间关联关系
- 覆盖常见业务状态
- 能支持前后端联调
- 能支持接口测试
- 能支持功能测试
- 能支持异常场景测试

的测试数据。

---

# 一、先分析数据库，不要立即生成数据

在生成任何 SQL 之前，先扫描并分析当前项目。

重点寻找：

```text
*.sql
CREATE TABLE
Entity
Mapper
Mapper.xml
Repository
Service
Controller
DTO
VO
Enum
application.yml
application-dev.yml
```

识别：

1. 数据库类型
2. 数据库名称
3. 所有业务表
4. 每张表字段
5. 主键
6. 唯一索引
7. 普通索引
8. 非空约束
9. 默认值
10. 外键
11. 逻辑外键
12. 枚举字段
13. 状态字段
14. 租户字段
15. 逻辑删除字段
16. 创建人/创建时间
17. 更新人/更新时间
18. 数据权限字段
19. 表之间的依赖关系

不要仅根据字段名猜测。

优先级：

```text
数据库DDL / COMMENT
>
Entity注释
>
Enum / 常量
>
Service业务代码
>
Controller
>
字段名称推断
```

无法确认的地方明确标记：

```text

```

# 三、测试数据规模

默认生成一套中等规模测试数据。

如果没有特殊要求，按照以下规模设计：

```text

用户：
20~30条

角色：
3～10条
```

优先保证：

```text

>
数据数量
```

# 五、严格处理主键

先确定项目主键策略。

判断是否使用：

```text
AUTO_INCREMENT
UUID
Snowflake
MyBatis-Plus ASSIGN_ID
业务编码
联合主键
```

如果数据库使用自增主键：

优先不要手工指定主键，除非关联表需要明确 ID。

例如：

```sql
INSERT INTO sys_user(username, realname)
VALUES ('zhangsan', '张三');
```

如果为了保证关联关系需要指定固定 ID，则明确说明。

如果项目使用雪花 ID：

生成合法 bigint ID。

例如：

```text
1900000000000000001
1900000000000000002
```

不得超出 BIGINT 范围。

---

# 六、处理唯一约束

扫描：

```text
UNIQUE KEY
UNIQUE INDEX
```

保证测试数据不会违反唯一约束。

尤其注意：

- username
- phone
- email
- code
- order_no
- serial_number
- tenant_code

这些字段必须唯一。

例如：

```text
TEST_USER_001
TEST_USER_002

ORDER202608180001
ORDER202608180002
```

---

# 七、表之间必须保持关联一致

例如：

```text
user
 ↓
order
 ↓
order_item
```

则必须：

```text
order.user_id
```

对应真实存在的：

```text
user.id
```

同时：

```text
order_item.order_id
```

必须对应真实订单。

禁止出现孤儿数据：

```text
order.user_id = 999
```

但 user 表中不存在：

```text
id = 999
```

---

# 八、多对多关系正确生成

例如：

```text
sys_user
   ↓
sys_user_role
   ↓
sys_role
```

应该先创建：

```text
用户
角色
```

然后创建：

```text
用户角色关系
```

保证关系完整。

---

# 九、考虑多租户

如果项目存在：

```text
tenant_id
```

则必须按照多租户规则生成数据。

例如生成：

```text
租户1001
杭州测试机构

租户1002
深圳测试机构
```

数据需要严格隔离：

```text
tenant_id = 1001
```

的数据只能关联：

```text
tenant_id = 1001
```

的数据。

禁止：

```text
租户1001订单
关联
租户1002用户
```

除非项目本身允许跨租户。

---

# 十、逻辑删除字段

如果存在：

```text
del_flag
deleted
is_deleted
```

不要所有数据都是：

```text
0
```

建议生成：

```text
正常数据：90%
逻辑删除：10%
```

前提是业务允许。

例如：

```text
0 = 正常
1 = 删除
```

必须先确认实际枚举定义。

---

# 十一、状态字段覆盖多个状态

如果存在：

```text
status
state
audit_status
pay_status
order_status
```

不能全部生成同一个状态。

需要根据项目 Enum / 常量确认状态值。

例如订单：

```text
待支付
已支付
处理中
已完成
已取消
```

按照合理比例生成。

例如：

```text
待支付：20%
已支付：30%
已完成：30%
已取消：10%
其他：10%
```

---

# 十二、时间字段要有业务合理性

生成：

```text
create_time
update_time
start_time
end_time
pay_time
finish_time
expire_time
```

时必须满足时间逻辑。

例如：

```text
create_time
<
pay_time
<
finish_time
```

不能出现：

```text
完成时间早于创建时间
```

默认测试数据时间范围可以设置在：

```text
最近30～90天
```

并生成：

```text
今天
昨天
最近7天
最近30天
```

的数据，方便测试查询和统计功能。

---

# 十三、金额字段合理生成

如果存在：

```text
price
amount
total_amount
pay_amount
discount_amount
refund_amount
```

必须符合业务逻辑。

例如：

```text
total_amount = 100
discount_amount = 20
pay_amount = 80
```

而不是：

```text
total_amount = 100
pay_amount = 500
```

除非项目业务有特殊含义。

金额字段必须避免明显异常。

---

# 十四、手机号、身份证、邮箱等敏感数据

测试数据必须使用虚构数据。

禁止生成真实个人敏感信息。

手机号使用明显测试数据，例如：

```text
13800000001
13800000002
13800000003
```

邮箱：

```text
test001@example.com
test002@example.com
```

身份证等字段，如果不是业务必须：

优先生成格式正确但明确为测试用途的数据。

不得复制生产环境真实数据。

---

# 十五、密码字段

如果用户表存在密码字段：

不要直接写：

```text
123456
```

除非系统本身明确存明文。

如果项目使用：

```text
BCrypt
MD5 + salt
PBKDF2
Argon2
```

根据实际项目加密方式生成。

同时在 SQL 注释中说明测试账号原始密码，例如：

```text
测试密码：123456
```

数据库中保存真实项目使用的加密结果。

---

# 十六、树形数据

如果存在：

```text
parent_id
pid
parent_code
tree_path
```

需要正确生成树结构。

例如：

```text
总部
├─ 技术部
│  ├─ 后端组
│  └─ 前端组
└─ 产品部
```

保证：

```text
parent_id
```

引用正确。

避免：

```text
A的parent是B
B的parent又是A
```

产生循环。

---

# 十七、字典数据

如果项目有：

```text
sys_dict
sys_dict_item
```

或者类似字典系统：

优先使用项目已有字典。

不要随意创建重复字典。

业务表中：

```text
status
type
category
```

等字段值必须符合字典表定义。

```text
逻辑删除
```

用于测试：

- 过滤条件
- 分页
- 查询
- 排序

# 二十一、SQL执行顺序

必须根据依赖关系排序 SQL。

例如：

```text
1. tenant
2. department
3. user
4. role
5. user_role
6. product
7. orders
8. order_item
```

删除数据时反过来：

```text
1. order_item
2. orders
3. product
4. user_role
5. user
```

避免外键问题。

---

# 二十二、测试数据必须可重复执行

尽量设计为开发阶段可以重复执行。

优先考虑：

```sql
DELETE FROM xxx
WHERE create_by = 'TEST_DATA';
```

或者：

```text
username LIKE 'test_%'
```

清理旧测试数据后重新插入。

不要直接：

```sql
TRUNCATE TABLE
```

除非明确确认这张表可以清空。

尤其禁止破坏系统内置数据。

---

# 二十三、给测试数据增加统一标识

如果业务允许，测试数据统一使用明显标识。

例如：

```text
TEST_
DEV_
测试数据
```

比如：

```text
TEST_ORDER_001
TEST_USER_001
```

方便后续清理。

# 二十六、生成清理脚本

除了初始化 SQL，还必须生成对应的测试数据清理 SQL。

禁止删除非测试数据。

# 三十、安全要求

严格遵守：

1. 不连接生产数据库写入测试数据。
2. 不使用生产真实用户数据。
3. 不复制生产手机号、身份证、邮箱、Token。
4. 不输出数据库密码或 AccessKey。
5. 不执行 DROP DATABASE。
6. 不执行危险的全表 DELETE，除非明确确认。
7. 所有测试数据应该可以被明确识别和安全清理。

# 三十一、最终执行流程

请按照下面步骤执行：

第一步：

分析数据库结构。

第二步：

输出表依赖关系。

第三步：

确定需要生成测试数据的表。

第四步：

确定每张表生成多少数据。

第五步：

确定需要覆盖的业务状态。

第六步：

生成基础数据。

第七步：

生成业务数据。

第八步：

生成关系表数据。

第九步：

生成边界场景数据。

第十步：

检查：

```text
NOT NULL
UNIQUE
FOREIGN KEY
逻辑外键
枚举
租户
时间
金额
```

是否合法。

第十一步：

生成完整 SQL。

第十二步：

生成对应清理 SQL。

# 最终要求

不要一上来直接生成随机 INSERT。

先分析项目真实数据库结构，然后告诉我：

1. 数据库有哪些核心表
2. 表之间如何关联
3. 哪些表需要生成测试数据
4. 每张表计划生成多少条
5. 准备覆盖哪些业务场景
6. 有哪些字段或关系目前无法确认

分析完成后，再生成最终可执行测试数据 SQL。

所有生成的数据必须做到：

> 数据库层面可执行，业务层面合理，关联关系完整，方便测试，方便清理。
