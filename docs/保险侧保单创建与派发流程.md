# 保险侧保单创建与派发流程：谁创建保单、保单如何到达 App 用户

> 本文回答三个问题：**保单由谁创建？由谁"派发"给对应的 App 用户？这一系列流程长什么样？**
> 内容与当前代码一致（JeecgBoot `InsuranceImportController/Service`、
> `InsuranceAssignmentService.enrollUsers`、`InsuranceMobilePlanService`，
> 官网 BFF `insurer_assignment_routes.py`，App `InsurancePlanBindingViewModel`）。
> 配套文档：《保险侧保单数据设计.md》、《保险侧计划与保单设计及全流程闭环.md》、
> `backend/contracts/INSURANCE_BUSINESS_API.md`。

## 0. 一句话结论

- **保单由保险机构创建**：保险侧（机构管理员 / 保险运营员）通过 JeecgBoot 业务导入接口
  `POST /rehealth/insurance/v1/imports/policies` 创建，需权限 `rehealth:insurance:business:import`。
  官网目前没有保单导入页面（计划目录页面已有），保单以服务端对接 / 机构运营方式导入。
- **没有人工"派发"动作**：保单不是被"派发"出去的，而是通过 **租户级被保人假名
  `insured_subject_ref = sha256(tenantId:userId)`** 与被保人的 App 账号静态挂钩。
  App 用户登录后，系统按登录身份自动匹配出属于他的保单，用户本人勾选同意后完成
  **零输入绑定授权**——最终"落到用户头上"的动作由 App 用户本人完成（合规要求，
  服务端不做代授权）。

```mermaid
flowchart LR
    A["保险机构<br>导入参保人（手机号）<br>→ subject 假名 + enrollment"] --> B["保险机构<br>导入保单<br>policy.insured_subject_ref = 假名"]
    B --> C["App 用户登录<br>自动匹配自己的保单<br>（bindable-policies）"]
    C --> D["用户勾选同意 → bind<br>consent granted + plan_binding active"]
    D --> E["保险侧工作台可见<br>（授权是数据使用门槛）"]
```

## 1. 角色与职责总表

| 角色 | 动作 | 入口 / 接口 | 权限 |
| --- | --- | --- | --- |
| **App 用户** | 注册 App（手机号即账号） | `/sys/user/register` | 无需 |
| **保险机构（官网）** | 导入参保人：输入已注册 App 的手机号，建立被保人假名与参与关系（被保人池） | 官网「我的客户 → 导入参保人」→ BFF `POST /api/insurer/assignments/enrollments` → JeecgBoot `POST /rehealth/insurance/v1/assignments/enrollments` | `rehealth:insurance:assignment:manage` |
| **保险机构（服务端/运营）** | **创建保单**：批量导入保单，指定 `insuredSubjectRef`（被保人假名）与可选 `defaultPlanId` | JeecgBoot `POST /rehealth/insurance/v1/imports/policies` | `rehealth:insurance:business:import`（机构管理员 / 保险运营员 / admin） |
| **保险员工** | 认领被保人（服务关系，可选，管理员视角不需要） | 官网「被保人池 → 认领」→ `POST /api/insurer/assignments/claim` | `rehealth:insurance:assignment:manage` |
| **App 用户** | 查看候选保单 → 勾选"同意授权" → 加入 | App `GET /plans/bindable-policies` → `POST /plans/bind` | 本人动作（合规） |
| **保险侧（工作台）** | 授权后在工作台看到该用户，做风险分层 / 干预 / 关怀计划 | 官网「干预改善工作台」 | `rehealth:insurance:assignment:view` 等 |

## 2. 关键机制：被保人假名 `subject_ref`（保单与 App 用户的"挂钩点"）

保单不存手机号、不存 App 账号明文，只存 64 位假名：

```
subject_ref = sha256( tenantId + ":" + userId )   # 租户级假名，跨机构不可关联
```

- `userId` 是全局账号 ID（App 注册产生的 `sys_user`）。
- 同一自然人在不同保险机构各自生成**不同的假名**（前缀含 tenantId），机构间数据不可串。
- 假名的两条创建路径（都会返回/展示 subject_ref 给保险侧）：

```mermaid
flowchart TB
    subgraph 路径A[路径 A · 官网导入参保人（手机号）]
        A1["官网输入手机号（每行一个）"] --> A2["JeecgBoot enrollUsers：手机号 → userId"]
        A2 --> A3["upsert subject（假名=sha256）<br>+ enrollment(active)"]
        A3 --> A4["被保人池展示 subject_ref / 导入结果返回"]
    end
    subgraph 路径B[路径 B · 服务端导入参保人（rehealthUserId）]
        B1["保险侧系统调 POST /imports/subjects<br>{rehealthUserId, ...}"] --> B2["校验该用户是本租户 active member"]
        B2 --> B3["upsert subject（假名=sha256）"]
        B3 --> B4["批次结果逐行返回 subjectRef"]
    end
    A4 --> C["保险侧拿到 subject_ref<br>（后续填到保单导入 insuredSubjectRef）"]
    B4 --> C
```

> 保险侧**无需自己计算**假名：官网被保人池、`/imports/subjects` 批次结果、
> `/assignments/enrollments` 列表里都能拿到每条参保记录对应的 `subject_ref`。

## 3. 保单创建（导入）——谁、在哪、怎么建

### 3.1 入口与权限

| 项 | 值 |
| --- | --- |
| 接口 | `POST /rehealth/insurance/v1/imports/policies`（JeecgBoot，`X-Tenant-Id` 指定租户） |
| 权限 | `rehealth:insurance:business:import`（角色：机构管理员 `insurance_org_admin`、保险运营员 `insurance_operator`、`admin`） |
| 调用方 | 保险机构服务端 / 机构运营账号；官网前端暂未提供页面（可补，与参保人导入同模式，见 §7） |
| 幂等 | 行级：`(tenant_id, policy_no)` 唯一 upsert；批次级：`idempotencyKey` 重放直接返回原结果 |

### 3.2 请求字段（PolicyRow）

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `policyNo` | ✅ | 保单号，`(tenant_id, policy_no)` 唯一 |
| `policyType` | ✅ | 保单类型 |
| `insuredSubjectRef` | ✅ | **被保人假名（64 位 sha256 hex）**，必须已存在于本租户 `rehealth_insurance_subject`——即"先参保、后保单" |
| `defaultPlanId` | 可选 | 默认健康计划 ID（指向计划目录）；为空=仅保单、无计划（App 绑定为 `NONE` 占位授权） |
| `policyholderSubjectRef` | 可选 | 投保人假名（64 位 hex，可空） |
| `productCode` / `productName` | 可选 | 产品代码/名称（App 候选保单展示用） |
| `coverageAmount` / `premiumAmount` / `deductibleAmount` | 可选 | 保额 / 保费 / 免赔额 |
| `waitingPeriodDays` | 可选 | 等待期（非负） |
| `effectiveOn` / `expiresOn` | 可选 | 生效/失效日期（失效不得早于生效） |
| `status` | 可选 | 默认 `active` |

### 3.3 导入校验与落表

```mermaid
sequenceDiagram
    participant OP as 保险机构（服务端/运营）
    participant JEE as JeecgBoot InsuranceImportController
    participant DB as software_db
    OP->>JEE: POST /rehealth/insurance/v1/imports/policies<br>X-Tenant-Id + JWT（持 import 权限）
    JEE->>JEE: 权限校验 + 租户访问校验（requireTenant）
    JEE->>DB: 每行：insuredSubjectRef 必须为 64 位 hex<br>且存在于本租户 subject 表（先参保后保单）
    JEE->>DB: upsert rehealth_insurance_policy<br>（tenant+policyNo 唯一；默认 status=active）
    JEE-->>OP: 批次结果：逐行 created/updated + policyId<br>（idempotencyKey 重放时直接回放原批次结果）
```

落点：`rehealth_insurance_policy`（tenant_id、policy_no、insured_subject_ref、default_plan_id、status 等）。

## 4. 保单"派发"：假名自动匹配 + App 用户授权绑定

保单创建完成后**没有派发按钮**。真正让保单"到达"App 用户的是两步：

1. **系统自动匹配**（用户登录后即生效）：按登录账号找到他的假名，再找 `insured_subject_ref = 假名` 的有效保单；
2. **用户本人授权绑定**：App 勾选"同意授权"点「加入」，服务端写 consent + plan_binding。

### 4.1 匹配逻辑（bindable-policies）

```mermaid
flowchart TD
    A["App 登录用户 userId"] --> B["查所有 enrollment_status=active 的 subject<br>（可能在多家机构，各自不同假名）"]
    B --> C{"该租户是有效租户？"}
    C -- 否 --> D["跳过"]
    C -- 是 --> E["查 insured_subject_ref = 本租户假名<br>且 status=active 的保单，按生效日倒序"]
    E --> F["脱敏展示：尾号 XXXX + 产品名 + 计划名 hasPlan"]
```

- 候选保单脱敏（仅尾号 4 位）；多机构时按机构分组展示。
- 用户看到的就是"保险公司已经为这张保单挂好的自己"——无需输入保单号。

### 4.2 零输入绑定（bind）

```mermaid
sequenceDiagram
    participant U as App 用户
    participant JEE as JeecgBoot InsuranceMobilePlanService
    participant DB as software_db
    U->>JEE: POST /rehealth/mobile/insurance/plans/bind<br>{tenantId?, policyNo?, planId?, consentVersion, evidenceRef}
    JEE->>DB: ① 自动选租户：未指定时取唯一参保租户<br>（多租户报错要求选择）
    JEE->>DB: ② 自动选保单：未指定时取唯一有效保单<br>（多张报错要求选择）
    JEE->>DB: ③ 计划 = 保单 default_plan_id<br>（无计划保单 → planId=NONE 占位，仅授权不挂计划）
    JEE->>DB: ④ consent：status=granted（本人授权证据）<br>⑤ plan_binding：status=active
    JEE->>DB: ⑥ subject.consent_status=granted
    JEE-->>U: 绑定成功（planName 供 App 展示；NONE 时为空）
```

- 幂等：重复绑定（同租户+同假名+同保单+同计划）走 upsert，不产生重复记录。
- 授权后 `subject.consent_status=granted`，该用户进入保险侧工作台队列（授权是数据使用的合规门槛）。

### 4.3 "派发"一词的精确含义

| 通俗说法 | 系统实际机制 |
| --- | --- |
| 保险侧"把保单派给用户" | 导入保单时用 `insuredSubjectRef` 假名挂到该用户账号上 |
| 用户"收到保单" | App 按登录身份自动匹配 `bindable-policies` 展示 |
| 用户"签收" | 勾选同意 → bind → consent granted + plan_binding active |

## 6. 约束与幂等规则

1. **先参保、后保单**：`insuredSubjectRef` 必须已存在于本租户 subject 表，否则整行报错。
2. **租户级隔离**：`(tenant_id, policy_no)` 唯一；假名含 tenantId 前缀，跨机构不可关联。
3. **假名只接受 64 位 sha256 hex**：导入时强校验，防止误传手机号/明文身份。
4. **重复导入幂等**：同一保单号重复导入为 update，不产生重复保单；批次 `idempotencyKey` 重放直接回放原结果。
5. **绑定授权是用户本人动作**：服务端不做代授权；`consentVersion` 必填（用户勾选同意的版本证据）。
6. **计划可选**：`defaultPlanId` 为空时保单照常导入，用户绑定为 `planId=NONE` 占位（仅授权、不挂计划），App 显示"仅授权，暂无健康计划"；后续补录计划后同一保单可再次绑定切换。
7. **多保单/多机构需要用户选择**：自动匹配仅在"唯一参保租户 / 唯一有效保单"时零输入直通，否则 App 展示候选让用户点选。

## 7. 常见问题

**Q1：官网为什么没有"保单导入"页面？**
官网已提供参保人导入与计划目录页面；保单导入目前走 JeecgBoot 服务端接口
（`POST /rehealth/insurance/v1/imports/policies`，持 `rehealth:insurance:business:import` 权限），
供机构对接系统 / 运营批量导入。需要时可在官网补页面，与参保人导入同模式（BFF 转发、
浏览器不持有 Jeecg 服务凭据）。

**Q2：`insuredSubjectRef` 从哪来？**
从参保环节：官网被保人池每条记录含 `subject_ref`；`/imports/subjects` 导入结果逐行返回
`subjectRef`；`/assignments/enrollments` 列表同样返回。保险侧把它填进保单导入即可，
无需自行计算 sha256。

**Q3：保单导入成功了，为什么 App 里看不到？**
依次检查：① 该用户在本租户 enrollment 是否 active；② 保单 `status=active` 且
`insured_subject_ref` 与该用户本租户假名一致；③ 租户本身有效（`countActiveTenant`）。
多机构场景下需确认查的是该用户对应机构。

**Q4：同一机构下同一用户有多张保单会怎样？**
`bindable-policies` 全部展示；`bind` 不指定 `policyNo` 时会报"存在多张有效保单，请先选择保单"，
App 让用户点选一张再绑定。多机构同理需先选机构（自动带上对应租户）。
