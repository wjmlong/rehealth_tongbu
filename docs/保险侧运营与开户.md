## 第 1 部分 · App 用户开通方案（老年用户，讨论稿）（原文档：保险侧运营与开户.md）

## 保险侧开通 App 用户方案（面向老年用户）

> 讨论稿 · 用于与业务/领导对齐范围与决策点
> 关联系统：ReHealth App（Android）+ JeecgBoot 服务端 + ReHealth Core 官网（保险端）

## 1. 背景与问题

保险机构需要把自己的老年客户（被保险人）接入 ReHealth App，用于日常健康监测、风险筛查和干预关怀。目前存在三个缺口：

1. **App 用户只能老人自己注册**：手机号 + 短信验证码 + 设置密码，对老年人几乎不可用；
2. **保险侧没有开通入口**：官网的「成员管理」只能新增保险公司内部员工，不能为客户开 App 账号；
3. **没有关怀闭环**：开通后缺少激活状态跟踪、家属协助、失联提醒等运营能力。

## 2. 方案目标

**把注册和操作负担从老人身上转移到保险机构、代理人和家属身上。老人全程只需要做三件事：收一条短信 → 点一下（或报一个码）→ 戴上设备。**

## 3. 核心流程

```text
① 预开户（保险侧）     ② 激活（老人一步）    ③ 使用（免密）
──────────────      ──────────────      ──────────────
官网批量录入/CSV导入   →  短信链接或激活码    →  手机号+短信验证码登录
创建账号+入保险租户       老人点击/报码即可       无密码、持久登录
+绑定保单/干预计划                               设备码预绑定、问卷代填
        │                                          │
        └────────── ④ 保险侧管理看板 ──────────────┘
             激活状态跟踪 · 重发激活 · 失联提醒 · 数据脱敏
```

## 4. 关键设计点

| # | 设计点 | 说明 |
|---|---|---|
| 1 | **保险侧预开户** | 官网单个录入或 CSV 批量导入（手机号、姓名、保单号），一次创建账号、归入保险租户、绑定保单，老人零操作 |
| 2 | **两种激活方式** | ① 短信链接：老人点一下即激活（首选）；② 8 位激活码（72 小时有效）：代理人/家属电话报码，App 里输入 |
| 3 | **免密登录** | 手机号 + 短信验证码直接登录，不设密码、不记密码；后续可选运营商一键登录 |
| 4 | **设备与问卷代办** | 设备码预先录入，老人登录后自动绑定免配对；健康问卷由代理人/家属代填 |
| 5 | **保险侧管理看板** | 未激活/已激活/已绑设备/失联状态跟踪，支持重发激活短信、重置登录 |
| 6 | **合规与隐私** | 知情同意 + 代签记录；紧急联系人（子女）；手机号脱敏展示；操作留审计 |

## 5. 对现有系统的影响

| 系统 | 改动 |
|---|---|
| 服务端（JeecgBoot） | 新增预开户、激活码、免密登录 3 个接口 + 1 张激活码表；复用现有短信、租户、角色、保单能力 |
| 官网（保险端） | 新增「参保人管理」页（含批量导入、状态看板） |
| App（Android） | 新增激活页、免密登录页（大字体）；登录后持久在线，尽量不要求重新登录 |

整体改动可控：账号、租户、短信验证码、保单导入等基础能力均已具备，本方案主要补齐"保险侧开通 + 老人无感使用"这一段。

## 6. 分期计划

| 期次 | 内容 | 价值 |
|---|---|---|
| **一期** | 预开户 + 激活码 + 免密登录 | 打通最小闭环：保险侧能开通，老人能用起来 |
| **二期** | 短信链接激活、设备预绑定、问卷代填、大字体/语音引导 | 进一步降低老人操作负担 |
| **三期** | 家属共管、紧急联系人、异常告警、关怀计划运营 | 形成健康关怀闭环与保险服务价值 |

## 7. 需要领导拍板的决策点

1. **激活方式**：是否以"短信链接"为主（需要短信模板和链接点击跟踪，成本略高但老人体验最好）？
2. **代持手机号**：老人手机号常由子女代持，是否支持"账号属于老人、登录/联系手机号为子女"的分离模式？
3. **自助注册入口**：是否对老年用户默认关闭自助注册（只允许保险侧预开户，减少输错和投诉）？
4. **一期范围**：是否先按一期最小闭环立项，大字/语音等体验优化放到二期？

## 第 2 部分 · 新保险公司两阶段开户流程（原文档：保险侧运营与开户.md）

现有设计下，每新增一家保险公司，应执行“平台开户 + 机构自治”两阶段流程。平台管理员负责建立租户边界和首位管理员；保险机构管理员只能管理自己租户内的人员、角色、部门和投保人范围。

## 一、新增保险公司的标准流程

### 1. 平台管理员创建租户

在 JeecgBoot 租户管理中创建：

```text
租户名称：某某保险公司
状态：启用
租户 ID：系统生成，例如 1003
```

对应接口：

```http
POST /sys/tenant/add
```

要求平台账号拥有：

```text
system:tenant:add
```

创建后会同步初始化默认租户套餐，但不会自动创建保险业务人员。

### 2. 创建部门

通过 Jeecg 的部门管理创建该租户的组织结构，例如：

```text
某某保险
├── 健康险事业部
├── 运营部
├── 精算与研究部
├── 理赔部
└── 合规审计部
```

当前保险机构设置接口只能读取部门和调整人员所属部门，尚不能创建部门，因此部门仍由平台管理员或有 Jeecg 部门管理权限的租户管理员创建。

所有 `sys_depart` 必须使用新公司的 `tenant_id=1003`。

### 3. 创建首位机构管理员

新账号使用：

```http
POST /sys/user/addTenantUser
```

核心字段示例：

```json
{
  "username": "insurance_1003_admin",
  "realname": "机构管理员",
  "password": "首次登录临时密码",
  "relTenantIds": "1003",
  "selectedroles": "保险机构管理员角色ID",
  "selecteddeparts": "健康险事业部部门ID"
}
```

该账号需要：

```text
insurance_org_admin
```

这个角色可以管理：

- 机构资料；
- 成员状态；
- 成员部门；
- 保险业务角色；
- 部门经理与投保人负责人关系；
- 风险数据查看。

首位 `insurance_org_admin` 必须由平台管理员通过 Jeecg 角色管理分配。保险机构设置 API 不允许普通机构管理员自行创建另一个机构管理员，从而避免权限扩张。

### 4. 配置机构资料

机构管理员登录并选择当前租户后调用：

```http
PUT /rehealth/insurance/v1/settings/organization
X-Tenant-Id: 1003
```

示例：

```json
{
  "name": "某某保险股份有限公司",
  "licenseNo": "统一许可证编号",
  "insuranceType": "health_insurance",
  "complianceEmail": "compliance@example.com",
  "regulatoryEmail": "audit@example.com",
  "dataRetentionYears": 7,
  "maskSensitiveData": true,
  "accessLogEnabled": true
}
```

生产环境建议强制：

```text
maskSensitiveData=true
accessLogEnabled=true
```

## 二、后续如何增加机构工作人员

### 新员工还没有系统账号

通过 Jeecg 租户用户接口创建：

```http
POST /sys/user/addTenantUser
```

创建时必须指定：

- `relTenantIds`：当前保险公司租户；
- `selecteddeparts`：当前租户部门；
- 初始角色；
- 临时密码。

### 员工已经有系统账号

可以邀请账号加入当前租户：

```http
PUT /sys/tenant/invitationUserJoin
```

或者根据手机号邀请：

```http
POST /sys/tenant/invitationUser
```

加入后应检查：

```text
sys_user_tenant.user_id = 员工账号
sys_user_tenant.tenant_id = 当前保险租户
sys_user_tenant.status = 1
```

同一个账号可以属于多个保险公司，但部门、角色和数据范围必须分别配置。当前代码已经保证在一家保险公司调整部门时，不会删除该账号在其他保险公司的部门关系。

## 三、给人员分配部门和角色

机构管理员可以通过保险机构设置接口操作。

### 设置部门

```http
PUT /rehealth/insurance/v1/settings/members/{userId}/department
X-Tenant-Id: 1003
```

```json
{
  "departmentId": "department-id"
}
```

服务端会验证该部门属于租户 `1003`。

### 设置保险业务角色

```http
PUT /rehealth/insurance/v1/settings/members/{userId}/role
X-Tenant-Id: 1003
```

```json
{
  "roleCode": "insurance_operator"
}
```

目前机构设置接口支持以下业务角色：

| 角色 | 建议人员 | 能力 |
|---|---|---|
| `insurer_viewer` | 客户经理、查看人员 | 风险、研究、报告只读 |
| `insurer_analyst` | 精算、研究人员 | 创建研究、冻结快照、运行及审核 PSM |
| `insurance_operator` | 运营人员 | 导入保单/理赔、生成报告及结算 |
| `insurer_auditor` | 合规审计 | 风险、报告和审计证据只读 |
| `insurance_department_manager` | 部门经理 | 只查看分配给自己的投保人 |
| `insurance_org_admin` | 机构管理员 | 管理机构、成员、部门和负责人 |

当前保险设置接口一次给普通人员保留一个保险业务角色，符合最小权限原则。机构管理员角色需要通过 Jeecg 平台角色管理分配。

## 四、部门经理如何获得投保人范围

只分配 `insurance_department_manager` 角色还不够，还要配置负责关系：

```http
PUT /rehealth/insurance/v1/settings/assignments/{subjectRef}
X-Tenant-Id: 1003
```

```json
{
  "managerUserId": "manager-user-id",
  "departmentId": "department-id",
  "status": "active"
}
```

服务端会验证：

- 经理是当前租户有效成员；
- 经理账号正常；
- 部门属于当前租户；
- 经理属于该部门。

未分配给经理的投保人不会出现在该经理的风险列表、详情或看板中。

## 五、如何增加投保人

目前投保人导入要求 `rehealthUserId` 已经是保险租户有效成员。因此顺序必须是：

```text
创建或找到 ReHealth 用户
→ 加入保险租户
→ 用户完成保险项目授权
→ 导入投保人映射
→ 导入保单
→ 导入理赔
→ 配置部门经理负责关系
```

接口顺序：

```http
POST /rehealth/insurance/v1/imports/subjects
POST /rehealth/insurance/v1/imports/policies
POST /rehealth/insurance/v1/imports/claims
```

每批必须包含：

```text
sourceSystem
idempotencyKey
records
```

保险后台只使用不可逆 `subject_ref`，不应该向业务人员暴露原始用户 ID、手机号、身份证号或原始健康遥测。

## 六、员工离职或权限调整

### 暂时停用租户成员

```http
PUT /rehealth/insurance/v1/settings/members/{userId}/status
X-Tenant-Id: 1003
```

```json
{
  "status": "disabled"
}
```

这只停用该人员在当前保险公司的成员关系，不会停用其全局账号，也不会影响其在其他租户的工作。

停用后：

- 不能进入该保险租户；
- 不能查询保险数据；
- App 计划绑定、当前计划和反馈也会实时拒绝；
- 旧 Token 和旧业务映射不能绕过成员状态。

正式离职时还应：

1. 停用租户成员；
2. 停用其投保人负责人关系；
3. 转移其负责的 `subject_ref`；
4. 保留历史操作和审批记录；
5. 不删除既有审计证据。

## 七、推荐的日常职责划分

```text
ReHealth 平台管理员
  ├── 创建保险租户
  ├── 创建首位机构管理员
  ├── 分配 insurance_org_admin
  ├── 处理租户停用和异常权限
  └── 审计跨租户安全

保险机构管理员
  ├── 配置机构资料
  ├── 查看和启停租户成员
  ├── 分配部门
  ├── 分配保险业务角色
  └── 配置部门经理负责范围

保险运营/分析/审计人员
  └── 按角色执行导入、研究、报告、结算或审计
```

## 八、每家新保险公司的验收清单

上线前至少验证：

- A 公司账号不能访问 B 公司；
- 伪造 `X-Tenant-Id` 返回 `403`；
- 同一账号在 A 公司换部门不影响 B 公司；
- 部门经理只能看到分配给自己的投保人；
- 停用成员后旧会话不能继续访问；
- 相同保单号可分别存在于不同租户；
- 导入幂等键不会跨租户冲突；
- 导出文件不包含其他租户数据；
- 保险门户不展示原始遥测和直接身份信息；
- 审计日志能定位租户、操作人、资源和时间。

本次仅核对现有实现并给出操作流程，没有修改代码；工作区保持干净。

## 五、严格处理主键

先确定项目主键策略。

判断是否使用：

```text
AUTO_INCREMENT
UUID
Snowflake
MyBatis-Plus ASSIGN_ID
业务编码
联合主键
```

如果数据库使用自增主键：

优先不要手工指定主键，除非关联表需要明确 ID。

例如：

```sql
INSERT INTO sys_user(username, realname)
VALUES ('zhangsan', '张三');
```

如果为了保证关联关系需要指定固定 ID，则明确说明。

如果项目使用雪花 ID：

生成合法 bigint ID。

例如：

```text
1900000000000000001
1900000000000000002
```

不得超出 BIGINT 范围。

## 六、处理唯一约束

扫描：

```text
UNIQUE KEY
UNIQUE INDEX
```

保证测试数据不会违反唯一约束。

尤其注意：

- username
- phone
- email
- code
- order_no
- serial_number
- tenant_code

这些字段必须唯一。

例如：

```text
TEST_USER_001
TEST_USER_002

ORDER202608180001
ORDER202608180002
```

---

## 七、表之间必须保持关联一致

例如：

```text
user
 ↓
order
 ↓
order_item
```

则必须：

```text
order.user_id
```

对应真实存在的：

```text
user.id
```

同时：

```text
order_item.order_id
```

必须对应真实订单。

禁止出现孤儿数据：

```text
order.user_id = 999
```

但 user 表中不存在：

```text
id = 999
```

---

## 八、多对多关系正确生成

例如：

```text
sys_user
   ↓
sys_user_role
   ↓
sys_role
```

应该先创建：

```text
用户
角色
```

然后创建：

```text
用户角色关系
```

保证关系完整。

---

## 九、考虑多租户

如果项目存在：

```text
tenant_id
```

则必须按照多租户规则生成数据。

例如生成：

```text
租户1001
杭州测试机构

租户1002
深圳测试机构
```

数据需要严格隔离：

```text
tenant_id = 1001
```

的数据只能关联：

```text
tenant_id = 1001
```

的数据。

禁止：

```text
租户1001订单
关联
租户1002用户
```

除非项目本身允许跨租户。

---
