# 保险侧保单数据设计

> 本文档说明现有项目中"保单"如何建模、如何导入、如何与 App 授权绑定、如何在官网展示，
> 以及给某个被保人（如王老五）补充真实保单时需要提供哪些字段。
> 数据表结构与接口均与当前代码一致（`V20260812_2` 业务 schema、`V20260825_3` 默认计划字段、
> `V20260825_4` 计划目录表 + `InsuranceImportController` + `InsuranceMobilePlanService` + `InsurancePlanCatalogController`）。

## 1. 保单在保险业务模型中的位置

```mermaid
erDiagram
    rehealth_insurance_subject ||--o{ rehealth_insurance_policy : "insured_subject_ref 被保人"
    rehealth_insurance_subject ||--o{ rehealth_insurance_policy : "policyholder_subject_ref 投保人"
    rehealth_insurance_policy ||--o{ rehealth_insurance_coverage : "保障责任"
    rehealth_insurance_policy ||--o{ rehealth_insurance_claim : "理赔"
    rehealth_insurance_subject ||--o{ rehealth_insurance_consent : "授权"
    rehealth_insurance_consent ||--o{ rehealth_insurance_plan_binding : "绑定凭据"
    rehealth_insurance_policy ||--o{ rehealth_insurance_plan_binding : "保单绑定"
    rehealth_insurance_subject ||--o{ rehealth_insurance_intervention : "干预参与"

    rehealth_insurance_subject {
        varchar id PK "主体 ID"
        int tenant_id "租户"
        char64 subject_ref "租户级假名 sha256(tenant:userId)"
        varchar rehealth_user_id "App 用户 ID"
        varchar enrollment_status "参保状态 active"
        varchar consent_status "授权状态 pending/granted"
    }
    rehealth_insurance_policy {
        varchar id PK "保单 ID"
        int tenant_id "租户"
        varchar policy_no "保单号（租户内唯一）"
        varchar product_code "产品代码"
        varchar product_name "产品名称"
        varchar policy_type "险种类型"
        varchar policyholder_subject_ref "投保人假名"
        varchar insured_subject_ref "被保人假名"
        date effective_on "生效日"
        date expires_on "失效日"
        varchar status "状态 active"
        varchar source_system "来源系统"
        varchar source_record_id "来源记录 ID（幂等键）"
        longtext metadata_json "扩展元数据（渠道等）"
    }
```

核心约定：
- 保单不直接存身份证/手机号，只引用 **subject_ref 假名**（被保人/投保人分别引用）
- 每张保单属于一个**租户**（保险公司），`(tenant_id, policy_no)` 唯一
- `insured_subject_ref` **可空**（两步式派发）：留空=保单先进机构保单库（App 端不可见），
  之后按手机号分配；指定时须指向本租户已存在的参保人且在校验负责范围内

## 2. 保单表字段语义（`rehealth_insurance_policy`）

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `policy_no` | ✅ | 保单号，租户内唯一 |
| `product_code` / `product_name` | 可选 | 产品代码/名称（风险池展示 product_name） |
| `policy_type` | ✅ | 险种类型（如 health / life / accident，自由文本） |
| `default_plan_id` | 可选 | **默认健康计划 ID（保险侧导入保单时指定）**——App 零输入绑定时按它自动选计划 |
| `policyholder_subject_ref` | 可选 | 投保人假名（团单等场景投保人≠被保人） |
| `insured_subject_ref` | **可选** | 被保人假名（64 位 sha256 hex）。**两步式派发**：留空=保单先入库（App 端不可见），之后在「保单」页签按手机号分配；指定时须已存在于本租户且在校验负责范围内 |
| `assigned_at` | 可选 | 保单分配时间（两步式派发，导入指定被保人或「分配」时写入） |
| `coverage_amount` / `premium_amount` / `deductible_amount` | 可选 | 保额/保费/免赔额（结算与 RWE 用） |
| `waiting_period_days` | 可选 | 等待期（天） |
| `effective_on` / `expires_on` | 可选 | 生效/失效日期（控制有效期） |
| `status` | ✅ | `active` 等；App 绑定只认 active |
| `source_system` / `source_record_id` | ✅ | 来源系统与源记录号，构成幂等唯一键 |
| `metadata_json` | 可选 | 扩展信息；风险池从中读 `$.channel`（渠道） |

## 3. 关联表一览

| 表 | 与保单的关系 | 关键字段 |
| --- | --- | --- |
| `rehealth_insurance_coverage` | 保单下多条保障责任 | `policy_id`、`subject_ref`、`coverage_code/name`、`limit_amount`、起止日、`status` |
| `rehealth_insurance_claim` | 保单下多条理赔 | `policy_id`、`subject_ref`、`claim_type`、事件日、提交/决定日、`billed/approved/paid_amount`、币种、`outcome_code` |
| `rehealth_insurance_consent` | 被保人级授权（与保单解耦） | `subject_ref`、`consent_type/version`、`granted_at/revoked_at`、证据引用 |
| `rehealth_insurance_consent_record` | 绑定时的授权留痕 | `tenant_id`、`subject_ref`、`consent_type/version`、`status=granted` |
| `rehealth_insurance_plan_binding` | **保单 ↔ 健康计划 ↔ 授权** 的绑定 | `tenant_id`、`subject_ref`、`policy_id`、`plan_id`、`consent_id`、`status=active` |
| `rehealth_insurance_plan_catalog` | **产品级计划目录**：保单 `default_plan_id` 引用的计划标识及其展示名称 | `tenant_id + plan_id` 唯一、`name`（App/官网展示计划名称）、`description`、`status` |
| `rehealth_insurance_intervention` | 被保人参与的计划干预 | `subject_ref`、`plan_id`、`consent_id`、`enrolled_at/ended_at`、`last_feedback_at` |

计划目录（`rehealth_insurance_plan_catalog`，`V20260825_4`）保存产品级健康计划模板；对具体用户的
计划实例仍由关怀计划（`care_plan`）承载。官网"我的客户"页顶部「计划目录」弹窗通过
`GET/POST /rehealth/insurance/v1/plans`（BFF `/api/insurer/plans`）按租户查看/新增计划；App 的
`bindable-policies` 与绑定响应返回 `planName`，绑定后“已加入的机构计划”直接展示计划名称。
`V20260825_4` 已为本地验收租户预置 `PLAN-CHRONIC-2026`（慢病管理关怀计划）与
`PLAN-CVD-2025`（心血管风险改善计划）。

## 4. 保单生命周期

```mermaid
stateDiagram-v2
    [*] --> active: 导入（imports/policies）<br>effective_on 起生效
    active --> active: 重复导入（幂等更新）
    active --> expired: expires_on 到期<br>（状态不变，查询按日期过滤）
    active --> inactive: 退保/失效（status 更新）
    inactive --> [*]
```

- 状态字段目前主要使用 `active`；到期与否由 `effective_on/expires_on` 判断
- **App 绑定只接受 `status='active'` 且 `insured_subject_ref` 与当前用户 subject 一致的保单**

## 5. 三条核心流程

### 5.1 保单入库与分配（官网「导入保单」→「分配」/ 服务端批量导入）

```mermaid
sequenceDiagram
    participant M as 保险经理（官网）
    participant BFF as 官网 BFF
    participant JEE as JeecgBoot
    participant DB as software_db
    M->>BFF: 「导入保单」弹窗：GET /api/insurer/policies/dispatchable-subjects<br>（负责用户下拉，可留空）+ GET 计划目录
    M->>BFF: 逐行填保单号/类型/产品/计划/生效日期<br>被保人可留空（先入库）
    BFF->>JEE: POST /api/insurer/policies/import → POST /rehealth/insurance/v1/imports/policies
    JEE->>DB: 指定被保人 → 校验存在于本租户 + 负责范围（越权 403）<br>未指定 → insured_subject_ref=NULL 进入保单库
    JEE->>DB: 按 (tenant, policy_no) 幂等 upsert
    JEE-->>M: 批处理结果（created/updated）；「保单」页签展示（未分配标记）
    M->>BFF: 对未分配保单点「分配」，输入用户注册手机号
    BFF->>JEE: POST /api/insurer/policies/assign {policyNo, phone}
    JEE->>DB: 校验：保单 active、手机号已注册 App、本机构已参保、<br>负责范围内、未分配他人 → 写入假名 + assigned_at
    JEE-->>M: 分配成功；App 端该用户即可看到保单并授权绑定
```

导入单行（`PolicyRow`）字段：`policyNo`（必填）、`productCode/productName`、`policyType`（必填）、
`policyholderSubjectRef`（可选）、`insuredSubjectRef`（**可选** 64 位假名，官网下拉自动带上；留空先入库）、金额三件套、`waitingPeriodDays`、
`effectiveOn/expiresOn`、`status`、`sourceRecordId`、`metadata`。

> 说明：官网「我的客户」页已上线「导入保单」弹窗（被保人可选）、「保单」页签与「分配」操作
> （BFF 转发，浏览器不持有 Jeecg 凭据），权限 `rehealth:insurance:business:import`
> （机构管理员 / 保险经理 / 运营员）。未分配保单对全部导入人可见、App 端不可见；已分配保单
> 按负责范围可见。核心系统对接仍可直连 JeecgBoot 批量导入接口，
> 官网 `/api/insurer/workflow/imports/policies` 支持 CSV/XLSX 文件导入。

### 5.2 App 绑定授权（用户进入干预工作台的授权环节）

```mermaid
sequenceDiagram
    participant APP as App 用户
    participant JEE as JeecgBoot
    participant DB as software_db
    APP->>JEE: GET /plans/bindable-policies<br>（显示候选保单：脱敏保单号+产品名+计划名称）
    JEE-->>APP: 候选保单列表（含 default_plan_id 与 planName）
    APP->>JEE: POST /plans/bind<br>{tenantId(可选), policyNo(可选), consentVersion, 同意证据}
    JEE->>DB: ① 自动选租户（当前用户唯一参保租户）<br>② 自动选保单（唯一有效保单；多张时报候选）<br>③ 自动选计划 = 保单 default_plan_id<br>（保单无计划 → planId=NONE 占位，仅授权不挂计划）
    JEE->>DB: ④ 授权：consent(status=granted)<br>⑤ 绑定：plan_binding(status=active)
    JEE-->>APP: 绑定成功（含计划目录 planName）→ 工作台该用户可见（consent=granted）
```

**零输入绑定**：用户不需要输入保单号、计划 ID——只需看到候选保单、勾选"同意授权"、点"加入"。
多保单/多机构时用户点选一次保单（App 自动带上对应租户与保单号）。
**计划可选**：保单 `default_plan_id` 为空时绑定照常成功，`plan_binding.plan_id='NONE'` 占位
（仅授权、不挂计划），`planName` 为空、App 显示"仅授权，暂无健康计划"；后续补录计划后
同一保单可再次绑定切换。

## 6. 幂等与租户隔离规则

1. `(tenant_id, policy_no)` 唯一 → 同保单号重复导入是更新，不会重复建保单
2. `(tenant_id, source_system, source_record_id)` 唯一 → 来源系统幂等键
3. 被保人假名必须在**同一租户**内已存在，跨租户保单导入直接拒绝
4. 保单不含任何直接身份标识；外部证件号只存哈希（`external_subject_ref_hash`）

| 险种 `policy_type` | ✅ | `health`（健康险） | 真实险种 |

## 8. 常见问题

- **保单导不进去**：`insuredSubjectRef` 不在本租户 → 先导入/参保该用户（官网"导入参保人"）
- **App 绑定失败**：保单未生效/已失效、被保人假名不匹配、用户无 active 参保关系
- **绑定后只显示计划 ID 不显示名称**：`default_plan_id` 不在当前租户计划目录中，官网"我的客户 → 计划目录"新增对应计划后再导入/更新保单
- **保单显示"未命名产品"**：`product_name` 未填，风险池展示为空
- **重复导入**：同 `policy_no` 会覆盖更新，不会产生两张保单
